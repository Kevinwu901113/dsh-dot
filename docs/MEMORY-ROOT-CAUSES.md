# 记忆系统在 chat-memory-benchmark 2.2 上失分的根因（2026-11-14）

依据：0.22.1 在 2.2 开发集三个榜的真实运行（2026-11-11，总分 S 38.3，加权 A 47.1）留下的全部产物——每题的提示词、回答、判分、账单，以及运行结束时的记忆目录（`memory.json`、`calls.jsonl`、召回索引）。
下面每条都写明证据是"已证实"（用运行数据重放或复现过）还是"推断"。只记录根因，不含改法。

## 分丢在哪（独立分析的结果）

| 失分来源 | 短榜 M01 | 长榜 M02 |
|---|---:|---:|
| 需要的原话没完整进提示词 | 35.9 | 42.3 |
| 进了提示词但没用上或用错 | 15.3 | 13.2 |
| 到期主动提起（成对题） | 5.7 | 5.2 |
| 合计（100 − A） | 57.2 | 60.8 |

成本另扣 7.4–11.8 分（C 是参照值的 5.5–15.4 倍）。自然榜：克制侧 P 97.5，想起侧 R 36.6。

## 根因一：笔记写满后，新内容被静默丢弃【已证实】

做法：把两次运行里每一次整理（consolidation）的输出，用 `applyExtraction` 原样重放；重放出的最终状态与保存的 `memory.json` 完全一致（条目数逐项相同）。

| | M01 | M02 |
|---|---:|---:|
| owner 想新增 | 616 | 1485 |
| 其中因超限被拒 | 581 | 1478 |
| self 想新增 | 509 | 961 |
| 其中因超限被拒 | 443 | 902 |
| owner + self 的 replace / remove 合计 | 52 | 84 |

- 第一个月写满（owner 1375 字、self 2200 字）后，几乎每条新增都被拒；self 在两个人物上从未被 remove，replace 合计 2 次。
- `memory.extract` 提示词给模型看已有条目，但不给容量和用量；`bankOp` 超限返回错误，`applyExtraction` 只记进 `report.errors`，不重试、不反馈。模型不知道满了，所以一直 add。
- 结果：笔记停在头两三周（M01 最后一题时 owner 里的日期只有 09-07 到 09-17，还留着"快递后天到"这类临时状态）；self 里大量是一次性的承诺和建议，不是长期事实。
- 这些整理调用占 C 的 47.6% / 40.1% / 70.7%（短 / 长 / 自然），产出绝大部分被丢弃。

## 根因二：检索只用叫醒她的那句话的字面去找【已证实】

做法：离线复现候选阶段（e5 余弦前 20 ∪ BM25 前 20，索引取提问时刻、去掉最近 6 轮）。运行中实际召回的 6466 轮 100% 落在复现的候选集里。

| 答题需要的原话在哪 | M01（789 轮） | M02（774 轮） |
|---|---:|---:|
| 最近 6 轮窗口 | 6% | 11% |
| 被召回 | 41% | 34% |
| 进了候选，被重排或预算挤掉 | 10% | 18% |
| 从未进入候选 | 43% | 37% |

- 到期题：98% / 100% 从未进候选。暗考题：50% / 39%。
- 从未进候选的原话，两个通道里的最好名次中位数是 273 / 198，约一半在 300 名以外：加大候选数救不回来。
- 对照：同一个索引，把查询换成标准答案（理想查询的上限），需要的原话进候选的比例从 54% / 59% 升到 88% / 90%；暗考 45% / 54% → 93% / 97%；到期 2% / 0% → 88% / 100%。
- 结论：索引、按轮切分、向量模型都不是瓶颈；瓶颈是查询只有一条、且是字面消息。检索里也没有时间维度（1–3 天前的原话 62% / 41% 从未进候选）。
- 次要：进了候选又被挤掉的在 M02 上有 18%，与"每次最多 1500 token、按整轮注入"有关（M02 每题只注入 3–10 轮）。

## 根因三："还没了的事"没有过期和完成机制【已证实】

- 条目只有模型标 `done` 才会离开；全程 done 只有 72 次（M01）和 204 次（M02），而新增是 353 和 1342 条。
- 超出 800 字时按"紧急度"挪去搁置：答应过（owed）+2，有到期日 +1。模型几乎给每条都标了 owed 和 due，于是过期条目长期占着可见位置，新来的无期限条目一加进来就被挪走。M01 最后的 20 条里 16 条是一个多月前已过期的。
- 搁置区上限 200，只留标题（14 字）；M02 被搁置 1237 条，至少一千条彻底丢失。
- 到期当天没有任何代码把今天到期的条目挑出来；`due` 只渲染成一句后缀。
- 到期题 27 + 18 道只过 1 道。其中 M01 有 11 道，对应条目就在可见列表里且标着今天到期，仍没提（见根因四）。

## 根因四：提示词在压着她用记忆【推断，未做对照实验】

- `memory.standing` 的说明："用的时候只说问到的""不相干的旧事别顺手带出来""和他现在明确说的冲突时以现在为准"；`memory.recall.header`："用不上就当没看见"。
- 现象：证据都在提示词里时，M01 暗考题通过率 43.8%，明问题 78.8%；假前提题证据多数在提示词里（71% / 64%），通过率 14.3% / 35.7%，回答顺着用户的错话说。
- 这些指令同时是自然榜克制率 95.5%、编造率 0 的来源，放松它们有代价。

## 已排除

- 索引、切分、向量模型（根因二的对照实验）。
- 原话被截断：证据轮在提示词里的可见比例 89–95%，与通过率无关。
- 判分：人工复核 45 条，1 条明显判错、1 条可商榷，不影响分数。
- 日记：只写给面板看，从不读回；不影响成绩，只计成本。

## 读这些数字要注意

- 适配器只给最近 6 轮；真实使用时当前会话的原话都在上下文里，一天内的事实表现会比这里好。根因一、三与此无关；根因二里超过会话范围的部分与此无关。
- 官方参照成本是在约 120 题抽样上算的，本次跑全量；换算到同一题数，短榜和长榜的 S 各高约 4 分。
- 复现脚本：`replay.mjs`（重放整理结果）、`retr.mjs`（候选阶段复现和理想查询对照）。独立分析全文另存。
